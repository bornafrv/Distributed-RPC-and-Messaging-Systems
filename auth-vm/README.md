auth-vm README
The auth-vm service is the dedicated authentication component of the distributed multi-VM system. Its main purpose is to isolate user credential storage and verification from the web front-end (web-vm), so the web server never reads user data directly and never performs local password validation. Instead, auth-vm runs as an independent backend service on its own virtual machine (VM2) and exposes a remote authentication API that other machines can call over the network. This design follows the project requirement to separate responsibilities across VMs and to ensure that sensitive authentication logic and user records remain on the authentication machine only, while VM1 simply orchestrates the login flow by forwarding credentials for verification.

Communication between web-vm and auth-vm is implemented using JSON-RPC over TCP via Go’s built-in net/rpc/jsonrpc package. This choice was made because it is lightweight, requires no extra third‑party framework, and provides a clean RPC interface suitable for inter-VM communication. auth-vm registers an RPC service (for example AuthService) and exposes an authentication method (for example Authenticate) that receives a username and password from the client and returns a success/failure result (and optionally a message). The server listens on a configurable TCP port, accepts JSON-RPC connections, and serves requests concurrently. This keeps the system architecture simple: web-vm is the only public HTTP server, while auth-vm is a private RPC backend reachable only over the internal VM network.

User accounts are stored on auth-vm in a local JSON file (commonly users.json) containing at least the required number of test users. Operationally, auth-vm is designed to be started as a standalone service process: once running, it waits for JSON-RPC connections from web-vm and answers authentication requests in real time. The expected runtime flow is that a user submits the login form to web-vm, web-vm forwards the credentials to auth-vm via JSON-RPC, auth-vm validates the username and password hash, and then web-vm decides whether to create a session and redirect the user or to display a login error. With this approach, auth-vm remains small, focused, and secure: it performs only authentication-related work, keeps the user database on VM2 as required, and exposes only the minimal RPC surface needed by the rest of the distributed system.

To run auth-vm in a clean environment, Go must be installed on VM2 and the service directory must contain the module files and user database. After setting the correct listening address/port (and ensuring that VM1 can reach VM2 over the network), the service can be built and launched with standard Go tooling. Once running, it can be tested indirectly through the web-vm login process (recommended), or directly by using a small JSON-RPC client to call the authentication method. Successful tests should confirm that valid users authenticate correctly, invalid usernames are rejected, incorrect passwords fail verification, and that no user data needs to be copied to VM1 at any time. This completes the auth-vm portion of the distributed implementation and provides a solid authentication foundation for the rest of the system (including file access through file-vm and later monitoring extensions).
