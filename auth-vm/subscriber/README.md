README – Part 3: Adding Pub/Sub and High Memory Usage Alerting
This section extends the distributed multi-VM system developed in the previous part by introducing a simple Publish/Subscribe mechanism for operational monitoring and alerting. The main objective of this phase is to monitor the memory consumption of the web service running on VM1 and to publish an event whenever the memory usage exceeds a predefined threshold. According to the project statement, the system must periodically observe the memory usage of the web server, define a threshold for high consumption, publish an event when that threshold is crossed, and ensure that at least one subscriber is able to receive and display the alert. In this implementation, these requirements are satisfied by augmenting the web service with an internal memory monitor and by creating a separate subscriber component that listens for alert events. As a result, the original distributed application is no longer limited to synchronous request-response communication only, but is also enhanced with an event-driven notification mechanism that improves observability and demonstrates a simple distributed Pub/Sub architecture.

The design of this section intentionally keeps the monitoring pipeline lightweight and easy to understand while still preserving the spirit of distributed systems engineering. Rather than introducing a heavy external broker such as Redis, RabbitMQ, or NATS, the implementation uses a simple custom publisher-subscriber approach over HTTP and JSON. This choice is fully aligned with the educational nature of the project and with the acceptable implementation strategies listed in the assignment, which allow a basic Pub/Sub realization using TCP or HTTP. In this design, the web service acts as the publisher, and a dedicated subscriber process acts as the event consumer. Whenever the web server detects high memory usage, it creates a structured event and sends it as a JSON payload to the subscriber’s HTTP endpoint. This gives the system the essential behavior expected from a Pub/Sub solution: the producer of the event is decoupled from the manual observation of the system state, and an independent consumer receives and displays the notification. Although simple, this architecture clearly demonstrates asynchronous event publication and reception across distributed components.

The monitoring functionality was added directly to the web service running on VM1 because the project explicitly requires that the memory usage of the web server be observed. To implement this, the service periodically reads runtime memory statistics using Go’s built-in runtime inspection capabilities. The recommended metrics in the assignment include values such as Alloc, HeapAlloc, and Sys, and in this implementation the primary metric used for threshold comparison is allocated memory, which provides a clear and direct measure of the active memory consumption of the process. A background goroutine was introduced to execute this monitoring cycle continuously at fixed intervals. During each cycle, the current memory usage is read, converted into megabytes, and compared against the configured threshold. If the observed value remains below the threshold, the system simply continues monitoring without external action. If the observed value rises above the threshold, the service publishes a high-memory event to the subscriber. This periodic and automated observation satisfies the requirement that memory usage must be monitored continuously rather than checked manually or only on demand.

The threshold for alert generation is a central part of this section, and the assignment suggests a value such as 300 MB. In the implementation, a configurable threshold was defined so that the alerting behavior could be tested and demonstrated easily in different environments. The monitor continuously compares the current memory usage of the web process against this threshold and triggers the alert when the process exceeds the limit. To avoid repeatedly sending the same alert in a tight loop while memory remains high, the service also includes a small control mechanism that ensures the warning is not published endlessly for the same condition. In practice, once the alert has been sent, the system remembers that a warning has already been issued and suppresses duplicate notifications until memory usage returns to a safe state or is manually cleared. This makes the behavior cleaner and closer to what would be expected from a real monitoring system, where alert storms should be avoided whenever possible.

To make the memory alert feature practical and testable, a dedicated endpoint was added to the web server for intentionally increasing memory usage. The project statement explicitly mentions that the system should provide a mechanism for artificially increasing the web service’s memory consumption so that the alert path can be tested. For this reason, the implementation introduces an HTTP endpoint named /consume-memory, which accepts a parameter specifying how many megabytes should be allocated. When this endpoint is called, the server allocates a corresponding amount of memory and stores it in a global structure so that the allocated data remains referenced and is not immediately released by the garbage collector. This design detail is important because simply allocating memory inside a short-lived local scope would allow Go’s runtime to reclaim it too quickly, making the test unreliable. By preserving the allocated blocks in a shared variable, the memory usage increases in a measurable and repeatable way, allowing the monitoring goroutine to detect the change and publish the alert event once the threshold is crossed.

In addition to the artificial memory growth endpoint, the system also includes a clearing endpoint used to release the allocated memory after testing. This endpoint, implemented as /clear-memory, resets the retained memory structure and triggers cleanup so that the process returns to a lower memory state. This makes it possible to run repeated tests without restarting the web service each time. It also allows the alert-suppression flag to be reset so that a new alert can be published during the next high-memory simulation. Together, these two endpoints transform the monitoring mechanism from a static feature into a fully testable and demonstrable workflow. A reviewer or instructor can trigger memory growth manually, observe the threshold crossing, see the event publication, clear the memory, and repeat the process again, all through straightforward HTTP requests.

The published event itself follows the structure expected by the project. The assignment provides an example event containing fields such as the event type, service name, current memory consumption, threshold value, and timestamp. The implementation follows this format by creating a structured object that includes values such as "HIGH_MEMORY_USAGE" for the event type, "web-server" or an equivalent identifier for the service name, the measured memory usage in megabytes, the configured threshold in megabytes, and a timestamp showing when the event was generated. Representing the event as a JSON object makes it easy to inspect, transmit, and extend in the future. It also makes the subscriber implementation straightforward, since the receiver only needs to accept a JSON payload, decode it, and display the result. This structure not only satisfies the project’s expected event format but also aligns well with common operational event designs used in practical distributed systems.

The subscriber component is implemented as a separate lightweight application whose responsibility is to receive and display alert events. According to the assignment, at least one subscriber must receive the published event and show a warning after the threshold has been exceeded. In this project, the subscriber runs independently from the main services and exposes an HTTP endpoint that accepts incoming event data from the publisher. When the web service publishes a high-memory notification, the subscriber receives the JSON payload, decodes it, and prints a clear warning message along with the event details. This demonstrates that the event has successfully left the publisher and been consumed by another process, satisfying the core Pub/Sub requirement of the section. From a systems perspective, separating the subscriber from the web service is also beneficial because it reinforces the distributed nature of the design and avoids mixing the generation of events with their consumption and display.

One of the important strengths of this implementation is that it preserves the architecture built in the previous part while adding the new requirement in a clean and modular way. The existing distributed system already consisted of a web service on VM1, an authentication service on VM2, and a file service on VM3, all communicating over the network using JSON-RPC. This new section does not replace or break that architecture; instead, it extends the web service with a monitoring responsibility and adds a new event channel for notifications. The user login flow, authentication RPC calls, file listing, and file retrieval mechanisms remain unchanged and continue to work as before. The Pub/Sub extension therefore acts as an enhancement rather than a redesign. This is an important architectural quality because it shows that the system can evolve by adding new capabilities—such as monitoring and alerting—without tightly coupling them to the business logic of authentication and file access.

The implementation also remains faithful to the allowed technologies and protocols described in the assignment. For the RPC interactions between the web service and the authentication service, a JSON-RPC approach was used, which was one of the explicitly accepted options and a strong choice for a lightweight Go-based distributed system. For the Pub/Sub part, the assignment listed multiple acceptable options including custom HTTP/TCP Pub/Sub, Redis Pub/Sub, RabbitMQ, NATS, and WebSocket-based approaches. In this project, the custom HTTP plus JSON strategy was selected because it is simple, transparent, easy to deploy on independent VMs, and sufficient to demonstrate the required publish-subscribe behavior. This choice also avoids unnecessary operational overhead while still showing a correct conceptual implementation of distributed event notification. In an educational setting, this is a particularly reasonable tradeoff because it keeps the focus on system behavior and design rather than on external infrastructure management.

From a testing perspective, this section can be demonstrated in a clear step-by-step runtime scenario. First, the web service on VM1 is started normally along with the existing distributed system services. Then the subscriber process is launched and left waiting for incoming alert events. At this point, the memory consumption of the web service is still below the configured threshold, so no alert should be produced. Next, the /consume-memory endpoint is called with a sufficiently large value, such as 100 MB or another amount chosen to push the process over the threshold after one or more calls. The monitor running inside the web service detects the increased memory usage during its periodic check. Once the measured memory exceeds the threshold, the service constructs the high-memory event and publishes it to the subscriber endpoint. The subscriber then receives the event and displays a visible alert message containing the event data. This sequence directly matches the expected behavior described in the assignment: the service runs, the subscriber waits, memory grows, the threshold is exceeded, an event is published, and the subscriber displays the warning.

This section also contributes to the overall quality of the project by introducing an operational mindset into the distributed application. The earlier parts of the system focused on user-facing functionality and service decomposition, while this part adds observability and reactive system behavior. High memory consumption is one of the most common runtime concerns in server applications, and the addition of automated monitoring with event-based warning demonstrates a practical understanding of how distributed services can be supervised in production-like scenarios. Even though the implementation is intentionally simple, it captures the key concepts of threshold-based monitoring, event generation, asynchronous notification, and decoupled alert consumption. These are fundamental building blocks of more advanced distributed monitoring ecosystems, and their inclusion significantly strengthens the technical quality of the project.

In conclusion, this section successfully implements the Pub/Sub and memory alerting extension required by the assignment by monitoring the memory usage of the web server, defining a clear threshold for abnormal behavior, publishing a structured event when the threshold is exceeded, and delivering that event to at least one subscriber that receives and displays the alert. The chosen implementation is lightweight, modular, and fully integrated with the multi-VM architecture developed earlier. By combining Go runtime monitoring, HTTP-based event publication, JSON event formatting, a dedicated subscriber service, and a testable memory-consumption workflow, the final result is a complete and professional extension of the distributed system. It not only satisfies the formal requirements of the project but also demonstrates good architectural judgment, practical testability, and a clear understanding of event-driven monitoring in distributed environments.
