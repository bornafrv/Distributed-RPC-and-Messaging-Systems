file-vm README
The file-vm service is the dedicated file storage and file delivery component of the distributed system and runs independently on VM3. Its main responsibility is to host the project’s dataset (files and/or images) and make that content available to the web service (web-vm on VM1) through network-based requests. This separation is a core requirement of the assignment: VM1 must not rely on local file paths to access the content, and the files must physically reside on a different virtual machine so that file access is performed through real distributed communication. In this design, file-vm becomes the single authority for file availability and file content, while web-vm acts only as a consumer that requests lists of files and retrieves selected files over the network.

Inter-service communication between web-vm and file-vm is implemented using JSON-RPC over TCP with Go’s standard net/rpc engine and the net/rpc/jsonrpc codec. file-vm runs as an RPC server: it registers an exported service type (commonly FileService) and exposes remote methods that web-vm can call. The key methods implemented are a file listing method (for example FileService.ListFiles) and a file retrieval method (for example FileService.GetFile). ListFiles scans the configured storage directory on VM3 and returns the names (and optionally basic metadata) of the files that can be served. GetFile receives a requested filename, validates it, reads the corresponding file from disk, and returns the file’s raw bytes along with additional information such as MIME type (and optionally file size). This RPC-based approach was chosen intentionally because it matches the assignment’s suggestion that a real “file service” design is stronger than a trivial static HTTP file server, and it clearly demonstrates service decomposition and distributed remote access.

A key part of the file-vm implementation is that it treats file access as a controlled service operation rather than arbitrary filesystem exposure. The service reads only from a defined base directory (such as a files/ folder shipped with the project or created on VM3) and uses strict filename handling to prevent clients from accessing unintended filesystem paths. In practice, this means the server expects a simple filename from the client, and it can reject requests containing path traversal patterns or invalid names. This ensures that even though the service is running on a separate VM, it still follows safe access rules and only serves the intended dataset. This behavior is particularly important in a distributed project because VM1 is assumed to be less trusted and must not be able to browse VM3’s filesystem freely; instead, it can only request specific content through the RPC interface.

On the client side, web-vm uses file-vm’s RPC API to build the user experience after login. Once the user is authenticated by auth-vm, web-vm calls ListFiles to obtain the list of available content and renders it on the home page. When the user selects a file, web-vm calls GetFile to fetch the file bytes. web-vm then decides how to present the file depending on its MIME type: textual files can be rendered as text, while images can be displayed in the browser by encoding the bytes appropriately (for example as base64 data) and embedding them into the HTML response. Because file-vm returns the real bytes over the network, this confirms that the system is not “cheating” by reading local disk content on VM1 and that the content actually resides and is served from VM3 as required.

From an operational perspective, file-vm is designed to be started as a standalone daemon-like process on VM3. It listens on a dedicated TCP port for incoming JSON-RPC connections and serves multiple client requests over time. Because the architecture is service-oriented, file-vm can be deployed, restarted, or updated independently of the other components as long as its RPC interface remains stable. Configuration typically involves selecting the listening address/port and the storage directory where the files are located. Once the service is running and network connectivity between VM1 and VM3 is confirmed, web-vm can immediately begin making RPC calls to list and retrieve files.

Testing file-vm is naturally performed through the full system flow, since file retrieval is part of the post-login behavior. A correct setup is demonstrated when (1) the user logs into web-vm successfully using auth-vm, (2) the home page displays the file list returned from VM3, and (3) selecting a file results in web-vm showing the correct content that was fetched from VM3 via RPC. Additional direct tests can also be performed by writing a small JSON-RPC client to call ListFiles and GetFile directly against VM3, confirming that the server returns expected filenames, rejects invalid requests, and returns correct byte payloads for valid files.

In summary, file-vm fulfills the role of a remote file repository and delivery service in the distributed multi-VM architecture. It keeps the project files physically on VM3, provides a clean RPC interface for listing and fetching files, and ensures that web-vm can present content to users without any local disk dependency. By using JSON-RPC and by modeling file access as explicit service methods rather than as shared filesystem access, the implementation demonstrates clear service boundaries, correct distributed communication, and a stronger architectural solution than a basic static file server. This makes file-vm an essential part of the overall system and a core proof that the project’s file workflow is implemented as a real multi-machine distributed design.
